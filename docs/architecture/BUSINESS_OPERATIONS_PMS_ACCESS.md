# Hospitality access references and delivery

The hospitality domain owns the accepted physical-stay/assignment window and its access requests. A qualified operator owns manual key/card handover observations. An authenticated device adapter owns smart-device provisioning/revocation/readback truth. No business account, guest identity, device inventory authority, secret-distribution system or scheduler is duplicated.

`hospitality_access_configurations` retains immutable per-room versions, exact independent `COMMERCIAL_PMS_ACCESS_CONFIGURATION` approval, direct maker membership/role, method, opaque inventory/device/account references, provider ownership evidence when applicable, and at most seven days of authority. Maker membership bounds the expiry. DISABLED and newer versions never fall back to an old policy. Current direct PMS and inspection capabilities must support unattended policy authority; every public mutation additionally needs live PMS+inspection scope and recent MFA. Manual staff handover still requires that staff member's own current scoped MFA context.

The existing `access_grant_references` remains the public reference catalogue. Check-in, room move and checkout now append matching hospitality history/audit/outbox in their owning transaction. A configured room also creates an immutable original command in `hospitality_access_jobs`; an unconfigured/legacy room retains UNKNOWN without inventing a device action. Enabling a configuration never silently issues a credential to an old guest. An existing actual active stay may be attached explicitly with `/access-grants/{id}/request` after scoped/MFA/current-source validation.

Jobs bind exact organisation, property, room, stay, assignment, configuration, operation, accepted start/end, SHA256 digest and original idempotency key. Foreign keys and insert guards enforce the same source tuple/window. The accepted end is no later than the frozen local checkout deadline or configuration expiry. `hospitality_access_observations` retains immutable manual/provider/service origin, reference version, request digest and opaque evidence. Deferred guards require matching observation plus per-version audit/history for every outcome change; older initial history or an older identical audit cannot satisfy a later version. Never put passwords, keypad codes, provider tokens or credential secrets in these records, logs or APIs; a provider delivers actual secrets itself.

MANUAL_KEY/MANUAL_CARD commands wait for a qualified actual handover/return observation. The browser cannot acknowledge SMART_DEVICE truth. `reference.state=CONFIRMED` is historical delivery evidence; `effective_state` separately reports UNKNOWN, RECORDED_ACTIVE, REVOCATION_REQUIRED or REVOKED against current owning facts and authority. An expired, departed, superseded or revoked-maker grant is not presented as currently authorised, even before a worker tick. Retained historical delivery confirmation does not mean the key remains active after confirmed return. Security reads are tenant/property scoped, audited and no-store.

The existing minute cadence runs access source review and lease-based dispatch. Organisation fences protect source decisions; independent job leases/generations protect concurrent workers. External calls occur after commit, under an eight-second context and a stable command request/correlation ID, never inside a local database transaction. A dispatched command is looked up by its original key before another effect is considered. ABSENT must mean definitive absence with no in-flight original issue; it cannot mean a timeout. Late original success is retained and durably revoked when its source ended during the call. An expired claimant's lease is recovered without inventing a new issuance. Revocation retains the original configuration/device/issue identity, continues after maker authority ends and waits for ambiguous original issuance to be reconciled.

Failures retain UNKNOWN, bounded five-minute retry, safe error codes and quarantine after twelve retry attempts. Wrong request/credential proof quarantines immediately. A scoped qualified retry retains the same digest/key and reads back the original operation. New failures/quarantine and pending revocations queue encrypted Notification Service security alerts; no local email/SMS provider exists. Actual authority-source read failure rolls back its savepoint, retains a conservative revocation and surfaces a safe worker error. Pending configured access/revocation outcomes are hard night-audit checks and participate in its source digest. No physical cleanliness, guest departure or financial settlement is inferred.

`internal/integrations/smartaccess.API` is the typed authenticated-adapter port. Like the existing Owner adapter boundary, no live device provider is registered by default; unsupported smart-device configuration returns503. A real adapter must authenticate its provider/account, prove exact device ownership, implement original-key idempotent issue/revoke and authoritative lookup, bind every observation digest/credential reference, and guarantee that definitive revocation prevents late activation of that original issuance. The local fake tests establish contract/state-machine behavior only, not production provider authentication or physical device execution. A supported real provider contract/credentials/adapter registration and actual device readback remain necessary for live certification.

Migration00023 retains all historical unknown references and adds version/source/observation guards. Deployment must drain the older API/worker before applying this migration and runtime grants, then start a schema23-compatible image; older images do not write the newly required access audit evidence. Do not run an older image against these new write guards or remove them for rollback. Use a compatible immutable image or a forward fix. Real staging rollout remains operator-owned through an authorised repository/Actions transport.
