# Backend Foundation Blueprint

**Status:** Accepted baseline before backend implementation  
**Branch:** development

This document defines the non-negotiable backend conventions for CosmicForge Real Estate before the first production service is implemented.

## 1. Platform shape

The initial backend contains:

### Seven user-domain services
- marketplace-service
- individual-owner-service
- business-operations-service
- property-manager-service
- artisan-service
- professional-services-service
- admin-service

### Four shared platform services
- verification-service
- payment-service
- notification-service
- media-document-service

### Edge
- api-gateway

Total: **11 database-owning microservices + 1 API Gateway = 12 deployable backend components.**

There is no central Real Estate identity service. Each user-domain service owns its own accounts and authentication state.

## 2. Backend implementation stack

- Language: Go
- HTTP: Chi + net/http
- PostgreSQL driver/pool: pgx
- SQL generation: sqlc
- Migrations: Goose
- API contracts: OpenAPI 3.1
- JSON: UTF-8 JSON
- Cache/ephemeral coordination: Redis
- Durable async transport: NATS JetStream
- Logs: Go slog structured JSON
- Tracing/metrics: OpenTelemetry
- Deployment: Docker images, server-side Docker Compose
- Infrastructure: Terraform
- CI/CD: GitHub Actions

## 3. Go module boundary

Each deployable backend component is its own Go module.

- gateway/api-gateway -> own go.mod
- each services/* -> own go.mod
- shared/go -> own go.mod

A root go.work may reference them during development.

A service must not import another service's internal packages. Cross-service dependencies are contracts, APIs and events only.

Architecture CI must reject direct imports of another service module.

## 4. Database ownership

Every microservice owns one PostgreSQL database and one dedicated database credential.

No cross-database SELECT, JOIN, UPDATE, INSERT, DELETE, stored procedure, foreign key or database link is permitted between services.

Cross-service state is referenced by immutable IDs plus an owning domain/service field where ambiguity is possible.

## 5. Domain-owned accounts

Each user-domain service owns:
- users/accounts
- credentials
- sessions/refresh tokens
- devices
- email/phone verification state
- password recovery
- MFA state
- roles
- permissions
- organization/staff membership where that domain requires it
- account security/audit state

The shared Go auth/security packages contain reusable code only; they never create shared user persistence.

The same human may intentionally have separate accounts in different domains.

## 6. Identifier standard

All persistent public/entity identifiers use UUIDv7.

Rules:
- generated by the owning service;
- stored as PostgreSQL uuid;
- represented as canonical lowercase UUID strings at API/event boundaries;
- never reused after deletion;
- database integer sequences may exist only for internal non-public technical rows if they never leave the service.

Cross-domain user references use both domain and ID, for example:

```json
{
  "actor_domain": "individual-owner",
  "actor_id": "019..."
}
```

Do not infer identity equivalence from matching email, phone or name across domains.

## 7. Time standard

- PostgreSQL: timestamptz
- services: UTC internally
- API/events: RFC3339 timestamps with timezone
- clients perform local display conversion
- business time zones, where relevant to a property/booking, are stored explicitly as IANA zone names

## 8. Money standard

Money is never represented as binary floating point.

Canonical representation:
- amount_minor: signed integer in minor units
- currency: ISO 4217 uppercase code

Example: NGN 25,000.50 = amount_minor 2500050, currency NGN.

Payment-service owns financial ledger truth.

## 9. API separation

Client/public APIs:
- /api/v1/*

Authenticated service APIs:
- /internal/v1/*

External provider callbacks:
- /webhooks/v1/<provider>/*

Admin-only routes remain domain-owned and explicitly authorized; they are not made internal merely because an admin calls them.

## 10. Request context

All requests receive:
- request_id
- trace_id
- calling_service when service-to-service
- actor_domain when user-authenticated
- actor_id when user-authenticated
- organization_id where relevant
- idempotency_key where required

The same request_id/trace context is propagated across downstream calls/events where possible.

## 11. Public authentication

Each user-domain service issues its own user access tokens.

Baseline:
- JWT signed asymmetrically with Ed25519
- issuer uniquely identifies the domain
- audience identifies CosmicForge Real Estate APIs
- access token lifetime: 15 minutes
- refresh tokens: opaque random secrets, rotated on every use
- default refresh session maximum: 30 days, subject to domain/security policy
- refresh token hashes only are stored
- refresh-token reuse revokes the token family/session
- every token has kid, iat, exp and jti

Password baseline:
- Argon2id
- unique random salt
- parameters centrally defined in shared Go security code and versioned for future rehash
- passwords never logged or returned

Admin accounts require MFA before production release.

## 12. Service authentication

Service-to-service authentication is separate from user JWTs.

Each deployable service has its own service identity and Ed25519 key pair provisioned through secrets management.

Service JWT baseline:
- typ: service+jwt
- iss: calling service name
- aud: exact destination service or approved audience
- lifetime: maximum 5 minutes
- jti: unique
- signed with calling service private key

Receivers validate:
- issuer
- audience
- signature/kid
- expiration
- allowed caller for the operation

Internal authorization uses an allow-list/capability policy, not merely "valid service token".

## 13. API response rules

Success payloads use explicit resource shapes. Do not expose database rows directly.

Errors use the platform error envelope documented in ERROR_STANDARD.md.

Cursor pagination is the default for unbounded collections. Offset pagination is allowed only for bounded/admin reporting use cases where stable semantics are defined.

All APIs are versioned from the first release.

## 14. Idempotency

Idempotency is mandatory for operations that:
- move money;
- trigger external provider side effects;
- create a resource that a client may safely retry;
- process webhooks;
- publish/complete sensitive workflow transitions.

The Idempotency-Key header is used for applicable public/internal commands.

The service stores scope, actor/caller, request fingerprint, status and final response reference.

Reusing a key with a different request fingerprint is rejected.

## 15. Events and outbox

NATS JetStream delivery semantics are at-least-once.

All consumers must be idempotent.

For business state changes that must publish an event, the producer uses a transactional outbox written in the same PostgreSQL transaction as the authoritative state change.

Event contracts are versioned and immutable once published.

## 16. External provider isolation

Provider-specific code stays behind integration/adaptor boundaries.

- CF Meet: messaging, voice, video, privacy relay
- Paystack: payment rail, payment-service only
- Firebase: FCM, Crashlytics, Analytics, App Distribution
- Object storage: media-document-service
- Maps, KYC/KYB and registries: provider adapters

Domain code depends on interfaces/capabilities, not provider response structures.

## 17. Database migration policy

Migrations are owned per service.

Production schema changes follow expand -> migrate/backfill -> contract when a backwards-compatible transition is required.

A deployment must not require two services to change atomically.

Destructive changes require an explicit rollout/rollback plan.

## 18. Configuration and secrets

Configuration uses environment variables/config injection.

- no production secrets in Git;
- services fail fast on missing required configuration;
- secret values are never logged;
- staging and production credentials are isolated;
- key rotation must be possible without recompiling the service.

## 19. Reliability conventions

Every deployable service exposes:
- GET /health
- GET /ready
- GET /version

Outbound HTTP calls require explicit connect/request timeouts.

Retries are allowed only when the operation is safe/idempotent or the downstream contract explicitly provides idempotency.

Unknown external outcomes are resolved by read-back/status lookup before repeating a side effect.

## 20. Observability

Structured logs contain at minimum:
- timestamp
- level
- service
- environment
- message
- request_id
- trace_id when available

Never log:
- passwords
- refresh tokens
- raw access tokens
- payment secrets
- private signing keys
- full sensitive KYC documents

OpenTelemetry is the trace/metric instrumentation standard.

## 21. First build block

The first backend implementation block is:

1. shared Go foundation libraries
2. api-gateway
3. verification-service
4. media-document-service
5. notification-service

The payment-service contract/state model is frozen during foundation work even if full payment implementation follows later.

User-domain services then build on these foundations while owning their own authentication/account subsystems.
