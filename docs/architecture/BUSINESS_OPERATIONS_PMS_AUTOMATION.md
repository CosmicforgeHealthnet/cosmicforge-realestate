# Controlled hospitality day automation

Business Operations remains the authority for business-day audit and close. `operational_pms_days.go` exposes shared transaction-level validation/closure functions used by both manual HTTP commands and `ProcessPMSDayAutomation`. All existing source, current-snapshot, cutoff, hard-exception, closing-report and atomic rollover checks remain in those functions. Automatic close allows zero exceptions, including otherwise human-reviewable exceptions. It cannot supply an exception approval or fabricate recent human MFA.

Automation is optional and manual by default. POST `/api/v1/business/hospitality-day-automation` captures a versioned property-specific MANUAL, AUDIT_ONLY or CLOSE_IF_CLEAR policy. Non-manual policies require recent MFA, direct scoped `night_audit:write` authority that can also operate without per-action MFA, and an exact independent `COMMERCIAL_PMS_DAY_AUTOMATION` approval requiring `night_audit:approve`. Policies capture timezone, current hospitality cutoff version, maker membership/role, effective/expiration times and a one-to-seven-day batch bound. Expiry is at most seven days and cannot outlive the maker's membership. Temporary delegated authority cannot create an unattended grant.

Only the latest policy is considered. It is reloaded under the common organisation fence, as are revocations, current account/membership/role/grants/denies, KYB, canonical property status/timezone and cutoff version. A changed property/cutoff or an already-open day with a different captured policy requires manual review. Expiry, future effective dates, explicit revocation or a new MANUAL policy never reactivate an older policy. POST `/hospitality-day-automation/{id}/revoke` reduces authority with current scoped MFA, without requiring another independent approval. Recorded policy status is not a claim of execution eligibility.

The existing maintenance loop provides the cadence and per-domain bounded context; no new scheduler is introduced. A fair property cursor is checked after obtaining the organisation lock, preventing duplicate work across worker replicas. Before cutoff there is no automatic audit/close. After cutoff, the worker records an actual current audit and either retains BLOCKED exceptions, records AUDITED for read-only mode, or commits one close/report/rollover/history/outbox transaction. Source digests and unique run keys suppress unchanged duplicate work. Batch bounds limit overdue-day processing. Service-owned audit/day/close evidence uses `created_by_service=business-operations-service`, with no borrowed human session or actor.

Unexpected source-operation failures roll back to a savepoint while the owning transaction retains a SOURCE_REVIEW_REQUIRED run and a five-minute retry cursor. Twelve consecutive failures enter QUARANTINED and are skipped by periodic work. The API lists expose recorded policy, retry/quarantine status and immutable run evidence with sanitized error codes; raw database errors are not stored there. Worker errors still reach the existing logger. Repair the owning source/permissions, then capture a new independently approved current policy to reset quarantine. A broker outage cannot lose the committed local outbox. A failed transaction cannot publish a committed close.

Migration00020 adds policies, append-only revocations, immutable runs and retry cursors. Tenant/property foreign keys, per-property policy versions, null-safe source-run uniqueness, explicit service-actor constraints and deferred matching immutable history protect evidence. Existing migrations are unchanged. SQLC supplies the actual latest-policy query. Public read routes use property authorization before pagination; the Gateway's canonical Business route and internal-route isolation remain unchanged.

Tests execute disposable PostgreSQL: concurrent worker copies, no early close, one immutable service close, audit-only/manual behavior, actual open-cashier blocking, duplicate suppression, current membership/scope/MFA revocation, expiry, cutoff changes, old-day policy mismatch and no old-policy fallback. A real restricted PostgreSQL role loses SELECT on `folio_items`; this exercises rollback, durable retries, quarantine and authenticated reviewed recovery without disabling guards. Subsequent sections record the separate accepted no-show and source reconciliation modules. External smart-access execution remains unfinished.

## Accepted no-show and assignment release (schema21)

A separate arrival policy records the cancellation/PMS capabilities and financial exposure appropriate to no-show processing. It reuses the same current-authority evaluator, approval engine, service identity, organisation fence, source-failure savepoint/backoff/quarantine pattern and existing scheduler. `automatic_no_show` must be true in the original accepted reservation snapshot; enabling a later policy never opts old bookings in. Only the newest live unrevoked arrival policy can operate. Approved sources are currently DIRECT/WALK_IN/CORPORATE/GROUP; remote-source automation is not represented as complete.

The expiry is at most seven days and cannot outlive the maker's membership. The policy's fixed currency, per-reservation limit and persisted cumulative gross limit are independently approved; organization locking and database constraints prevent concurrent overspend. Direct cancellation and PMS grants must be usable without per-action MFA; temporary authority cannot create an unattended grant. Workers recheck current roles/scopes, restrictions and KYB on every attempted operation. Manual mode or append-only revocation reduces authority without another independent approval.

The canonical release core retains accepted no-show grace/retained-night/cancellation rules and immutable obligations. Civil gaps/folds use `hospitality.LocalInstant`. A confirmation after its accepted deadline needs manual review. Any physical stay, occupied/unknown/hazardous assignment, current source/risk conflict or missing committed backing blocks automatic action. Actual unoccupied assignments may be released before invoking the same canonical no-show command. No room is declared clean and no guest is recorded as having stayed. Service-owned root/history/run evidence, stock changes, financial references, outbox and an encrypted operator Notification request commit together. Source failures roll back all partial work; other bookings keep progressing.

Pending refund/settlement requests and unknown cancellation financial outcomes enter the night-audit hard checks and evidence digest. A known original collection is not an executed refund or final settlement. Payment/Admin handoff and current owning readback remain required; no worker impersonates an Admin or treats Notification queueing as delivery. Customer-facing consent-at-dispatch notifications remain Section11 work.

GET/POST `/hospitality-arrival-automation`, POST `/{id}/revoke` and GET `/hospitality-arrival-runs` use the canonical Business prefix, live trusted tenant/property scopes, versions and idempotency. Readbacks expose recorded lifecycle, used gross exposure and source-review count; a recorded policy is not a guarantee of current eligibility. After repairing source facts/permissions, a new independently approved policy explicitly resets bounded quarantine. Migrations/evidence are retained during rollback.

## Owning room/status/stay reconciliation (schema22)

`internal/hospitality/reconciliation.go` evaluates bounded, typed owning sources loaded through SQLC and the established stock-backing validator. `operational_pms_reconciliation.go` applies proven repairs under the same organisation fence, audit/outbox and immutable source-version rules as front-desk commands. A real arrival can restore stale occupancy; an actual released departure journal can mark only VACANT_DIRTY, respecting a later qualified inspection. Terminal never-occupied assignments need the canonical nested reservation-state snapshot before release. Missing/contradictory sources never imply vacancy or cleanliness.

The existing minute worker runs `ProcessPMSRooms` with fair due cursors, organisation locking, per-room savepoints, five-minute failure backoff and twelve-failure quarantine. Service-owned immutable reports contain bounded source references rather than guest/contact/payment data. Unexpected source failure opens a safety exception as well as recording quarantine evidence. Source safety exceptions and independent maintenance feed `inventory_pools.operational_hold` through the existing computed-hold trigger; pool state, allocation calendars and commitment authority remain separate. This maintenance is eventual on that cadence; it is not a new live-admission authority or scheduler.

Public source reads and report pagination are tenant/property scoped. Exact version/digest reconciliation requires current PMS+inspection authority and recent MFA, including cached replay checks. A qualified vacant-dirty observation additionally requires independent exact-digest approval and zero active/occupied owning sources. It cannot override maintenance, an actual stay or contradictory evidence. A source-consistent result resolves only its own room-safety exceptions. Physical departure/move retains existing hazards, while manual vacancy/readiness cannot hide a real guest. Recovery resets only the explicitly repaired room's cursor. Tests use genuine HTTP source journeys, concurrent workers, immutable guarded legacy projections and a real restricted PostgreSQL source role to prove failure, nonstarvation, quarantine and recovery.
