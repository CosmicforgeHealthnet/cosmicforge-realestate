# ADR-0012 — Payment financial foundation

Status: accepted implementation of the supplied v1.0 blueprint Sections 1–3; live activation unapproved. Effective 10 October 2026.

The Payment Service is the sole application authority for payment_db. Domain services remain authorities for registrations, accepted obligations, property rights, mandates, agreements and completion evidence. The existing Individual Owner payment.API contracts cover later release, beneficiary allocation, refund and statement workflows; this implementation deliberately does not impersonate that full API.

Reuse Go, Chi, pgx, Goose, shared serviceauth, money, UUIDv7, HTTP, observability, transactional outbox and testkit. SQLC generates reference reads. Handwritten SQL owns the multi-step journal transactions, locks, deferred constraints and recovery transitions; generated numeric fields use strings, never float money.

A financial identity represents a legal person or organization. An authenticated registration creates its stable domain/account binding and distinct role/entity/currency wallets without a provider. Verification can bind an additional authoritative domain account to the existing identity **before** that account is provisioned. Already provisioned identities are not automatically merged: resolving an existing duplicate requires a separately designed, verified history-preserving migration. Email, display name and listing authorship never authorize identity linkage. This conservative linkage ordering is an implementation clarification, not permission to merge legal parties or change the product model.

Each account belongs to one wallet (or platform accounting), one legal entity, currency and provider/merchant pool. dimension_ref reserves property, project, branch, agreement, obligation, appointment, job and entitlement dimensions for the owning workflow. Journals and entries are immutable, balanced at deferred commit, positive integer minor units and dimension-consistent. Entries cannot be appended after their creating transaction. Corrections reverse immutable originals. A database administrator capable of disabling triggers remains outside the application trust boundary; deploy a least-privilege service role and audited migration role.

Seven projections are disjoint. DEPOSIT is included exactly once in PROTECTED. New AVAILABLE credits require sufficient settled cash after reserve against every liability in that same pool; restrictions block AVAILABLE postings. No HTTP endpoint accepts arbitrary journals or balance changes. Identity restrictions are serialized with postings, audited, and require a signed Admin command. Restoration records two distinct approvers asserted by the authoritative Admin service; implementing its approval UI and human identity workflow is outside this service's scope.

Individual Owner inserts a durable registration-delivery record in the same transaction as registration. Its optional worker adapter calls the signed Payment registration contract, retains failures and recovers expired leases. Configuration absence leaves delivery pending and permits Owner startup. Future domains adopt the same controlled contract. No service reads another service's database.

Migration consequences: four new Payment migrations and Owner migration 00019; no alteration of existing Owner financial tables. Destructive rollback is blocked when retained financial records exist. Contract consequences: /api/v1/payments reads, signed /internal/v1 commands and finance.*.v1 events. Tests: real PostgreSQL provisioning, isolation, invariants, reversal, restrictions, concurrent debits, migration round trip and contract parity. No approved fees, split shares or release milestones have been changed.
