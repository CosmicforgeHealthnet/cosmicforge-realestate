# Provider integration and operations

This release enables local/test collection, verification and DVA adapters only. No provider credential or mock fallback is embedded. Runtime registration rejects production mode and declared custody, transfer or mandate capability. The three PAYMENT_LIVE_* flags default false and startup rejects true. Manual Payouts configuration is an approval record, not provider activation.

## Runtime and setup

API: go run ./cmd/api; worker: go run ./cmd/worker; migrations: go run ./cmd/migrate up from services/payment-service. API defaults :8080, worker health :8081. Both expose /health, /ready, /version; API readiness needs payment_db and worker readiness also checks JetStream. Provider-less API startup and wallet provisioning work. The worker requires NATS_URL; it publishes committed finance events and processes inbox/recovery jobs. Docker builds nonroot api/worker/migrate binaries. Image build and deployment certification remain CI/staging tasks.

Use infrastructure/docker/service-env/payment-service.env.example. Inject DATABASE_URL and Ed25519 service keys through secret management; *_FILE works for the shared secret loader and migrate database URL. PAYMENT_PROVIDER_CONFIG is a JSON array of explicit merchant-scoped policies; [] is valid. credentials_ref names a required secret environment variable, such as PAYSTACK_NG_TEST_KEY (or its _FILE). Keys must match sk_test_ mode; public-key credentials do not initialize charges. Credentials never appear in financial DTOs or logs.

Each provider entry needs generated UUIDv7 provider_account_id and pool_id, provider paystack, legal_entity, merchant_ref, mode test, countries, one currency, categories, capabilities, min_minor/max_minor, approved/operational, policy_version, credentials_ref and approval_ref. Optional dva_approved/manual_payouts_approved flags document externally established capability status; they do not approve custody. Settlement account and webhook references point to controlled configuration. Priority 0 is primary; alternatives require failover_eligible. Fee basis points order equal-priority routes; available_liquidity_minor and an intent's required_liquidity_minor constrain new routing. Liquidity configuration is not cash/custody proof.

Configure the gateway's existing GATEWAY_UPSTREAM_PAYMENT_SERVICE_URL and GATEWAY_WEBHOOK_ROUTES=paystack=payment-service. Trust the gateway key in Payment. Public wallet reads then route under /api/v1/payments; Paystack callbacks use /webhooks/v1/paystack/{provider_account_id}/callbacks. The gateway injects its audience-bound service JWT. Configure TLS callback URLs with Paystack for the correct merchant/mode. Keep internal routes private. Deploy service-specific broker publisher permissions for the configured prefix.finance.* subjects, peer key rotation and dead-letter alerts.

Configure PAYMENT_WALLET_SERVICE_URL in Individual Owner separately from its deferred PAYMENT_SERVICE_URL. Registration/backfill is queued atomically; domain jobs deliver signed ensure commands, retry outages and reclaim expired leases. Missing configuration retains pending rows. This adapter does not enable Owner release/refund/beneficiary/statement workflows. Future domains must issue canonical, authorized registration and obligation evidence through equivalent signed contracts.

## Paystack contract guide

Official contracts checked on 10 October 2026: [transactions](https://paystack.com/docs/api/transaction/), [customers](https://paystack.com/docs/api/customer/), [dedicated virtual accounts](https://paystack.com/docs/api/dedicated-virtual-account/), [settlements](https://paystack.com/docs/api/settlement/), [webhooks](https://paystack.com/docs/payments/webhooks/). These are technical contracts, not commercial/legal approval.

Initialization uses email, integer minor-unit amount represented as the provider's string field, currency, a durable generated reference, intent metadata and card/bank_transfer channels. No Paystack split_code or automatic settlement splits are configured. Checkout URLs must be HTTPS. Verification checks exact reference, amount, currency, intent metadata, mode and merchant. If transaction customer.integration is absent, a same-credential customer fetch establishes it. HTTP requests have bounded timeouts, response-size limits, denied redirects, trace transport and request correlation. Ambiguous HTTP failures remain UNKNOWN_OUTCOME and never initiate an alternate charge.

Collection state is REQUESTED/SUBMITTING/INITIALIZED/PENDING/PROCESSING/VERIFIED_SUCCESS/VERIFIED_FAILURE/UNKNOWN_OUTCOME or RECONCILIATION_EXCEPTION. Settlement state is distinct. FetchBalance/ListTransactions/FetchSettlement support provider observation; batch status changes append immutable evidence. Observation does not post SETTLED_CASH. Manual Payouts merchant liquidity is not legal escrow and not an individual user's bank deposit. Processing-fee observations do not determine who contractually bears the fee.

## DVA consent and recovery

Every eligible registration gets an internal wallet; DVA issuance is separate. A signed domain request must include own wallet, correct merchant, canonical verified customer details, consent reference/version/timestamps/expiry, authoritative current KYC reference and required transient identification fields. Bank number and BVN are not stored or logged. Account presentation is masked; a digest supplies uniqueness. A trusted domain must validate that supplied identity/customer details belong to that actor before sending this command.

Customer validation acceptance (HTTP 202) does not prove identification. Sync fetches current provider identification before Titan assignment. Customer creation is durably marked CUSTOMER_UNKNOWN before the request; repeating an ambiguous outcome reads the original merchant customer by canonical email rather than creating another. ASSIGNING is durable before DVA creation; an unknown result uses FindDVA/readback and never another assignment. Missing provider identification stays pending/error, never ACTIVE. Consent/KYC invalidation restricts provisioning and funding matching. Existing mappings must match the original customer, merchant/mode, external ID, bank and account digest; reassignment is rejected. Deactivation remains allowed after consent or verification expiry; an unassigned DVA is disabled locally without creating an external account. Existing external deactivation must be confirmed by provider status.

Accepted DVA collection receipts are read back and mapped by unique merchant/customer, live local consent/KYC, wallet currency/entity and active mapping. They credit only PAYMENT_PENDING and provider receivable exactly once. Unmatched transfers stay in durable inbox retry/review and do not credit an inferred user. Rejected identification or an ambiguous validation/assignment with no authoritative readback requires provider/operator resolution; no secret-based provisioning job fabricates completion. Re-consent, bank changes and history-preserving reassignment policy require later approved workflow work.

## Failure/recovery runbook

| Condition | Action and evidence |
|---|---|
| Initialization timeout/process crash | Read original intent/reference; worker recovery verifies after five seconds. Never switch/reinitialize that operation. A new transaction may choose another approved route. |
| Invalid callback signature | 401 before persistence; confirm merchant/mode secret and exact raw body, without logging it. |
| Accepted callback fails processing | Inspect normalized provider_inbox state/reference/attempts; retry is retained. Expired PROCESSING leases are reclaimed with a new fence token. |
| Inbox DEAD after 12 attempts | Investigate provider, mapping, KYC and reference context. Admin POST /provider-inbox/{id}/replay with evidence_ref; active leases cannot be overridden. Replay preserves the economic operation reference. |
| Reversal or merchant-balance mismatch | Pool stays restricted; immutable journal/evidence retained; inspect reconciliation exception and resolve through later approved forward-accounting policy. No direct balance edit or automatic unrestriction. |
| Broker unavailable | Outbox retains committed events; shared relay leases/retries and marks published only after durable ack. Restart can republish the same event ID; consumers must deduplicate. |
| Provider unknown DVA assignment | Sync reads original customer/account. Do not call assignment again or change mapping. Escalate if readback cannot establish the outcome. |
| Owner registration delivery pending | Check configured Payment URL, signing/trusted keys, owned database queue, next_attempt_at/lease_until and last_error_code. Restart domain jobs; retry is idempotent. Do not query payment_db from Owner. |
| Migration rollback on retained funds | Expected refusal. Use approved backup/restore or forward migration with immutable financial evidence. |

Read-only operational counts: pending/dead inbox and outbox rows, outstanding unknown intents, registration queue depth, reconciliation exceptions and pool restrictions. Telemetry includes HTTP traces, request correlation, payment.financial.commands, payment.provider.requests/duration, payment.webhook.retries and shared outbox metrics. Logs retain operation/reference IDs and safe codes, never raw provider bodies, signing/provider secrets, BVN or bank numbers. Deploy alerts for dead letters, unknown outcomes and mismatch growth; no staging alert delivery is certified locally.
