  0. Document status, authority and reading guide
  The V5 product document defines an Individual Property Owner platform for personally owned residential, commercial, land,
  sale and owner-operated short-let activity. It gives the owner direct control over property records, listings, customers,
  agreements, payments, maintenance and performance while preserving the owner as the underlying authority.
  This backend specification turns that product vision into an implementation contract for the existing CosmicForge Real
  Estate architecture. It is deliberately more detailed than the product document because backend engineering also requires
  concurrency rules, idempotency, state transition guards, audit trails, failure recovery, database constraints, service
  authentication, event contracts, background work and release certification.

  1. Executive implementation mandate
  Build `individual-owner-service` as the sole authoritative domain service for personally owned property operations. The
  service must support a single owner or personal portfolio, direct operation without compulsory management, optional
  property-specific delegated management, complete property history and direct customer interaction through the wider Real
  Estate ecosystem.
• The owner remains the primary authority for personally owned property at all times.
• Property verification and listing publication are separate controlled transitions.
• Every compulsory customer charge must be disclosed before commitment and versioned after acceptance.
• Delegation is property-specific, capability-specific, time-limited, revocable and never grants payout redirection authority by
  default.
• Financial, tenancy, inspection, maintenance and audit records survive the end of manager, tenant, guest or listing
  relationships.
• The service owns domain business state but does not own payment ledger truth, verification truth, raw media bytes, system
  notification delivery or human communications.

  1.1 Definition of done for the domain
• Every approved product capability has an owning module, data model and callable API or explicit integration contract.
• Every mutable business lifecycle has a guarded state machine and auditable transition history.

• Every side-effecting retryable command that can duplicate money, publication, booking, signature or external action uses

• Every business state change that must propagate to another service writes an outbox event in the same PostgreSQL

• All required CI, race, migration, contract, E2E, security and recovery gates pass before promotion to staging.

  4. IDs, references, money and time
• All persistent public entity IDs are UUIDv7 generated by this service.
• Cross-domain people/entities carry both owning domain/service and ID; matching email/phone never implies identity
  equivalence.
• All timestamps are UTC `timestamptz` internally and RFC3339 over APIs/events; property/booking timezone is stored as an
  IANA name.
• Money is `amount_minor int64 + ISO-4217 currency`; no floating point money.
• Any accepted price/fee snapshot is immutable and linked by version ID to the resulting application/offer/booking/agreement.
• External service references are stored with service name, external ID, lifecycle status projection and last-synced timestamp
  where needed.


  5. Authentication, owner roles and authorization
  Because the platform has no central identity service, `individual-owner-service` implements its own account and
  authentication persistence using the certified shared Go security packages.

  5.1 Account/security capabilities
• Email+password, mobile/OTP and supported OAuth/OIDC sign-in adapters.
• Email/phone verification, password reset, recovery codes, trusted devices and active session management.
• Ed25519 access JWT, 15-minute default, rotating hashed refresh tokens, reuse detection and remote revocation.
• TOTP authenticator MFA; SMS/email second factor through Notification Service; step-up auth for payout changes, sensitive
  documents and property transfers.
• Biometric sign-in is a client capability that unlocks locally protected credentials/session; the backend never receives raw
  biometric data.
• Suspicious login/device alerts and security event audit.
• Account status: PENDING_VERIFICATION, ACTIVE, RESTRICTED, SUSPENDED, CLOSURE_PENDING, CLOSED.

  6.1 Required database constraints and indexes
• Unique active account per normalized verified primary email/phone within this domain, with soft-closure semantics defined
  explicitly.
• Unique property ownership root per persistent property record; duplicate claims are represented as conflict cases, not
  duplicate authoritative property rows.
• Only one active published listing per property/unit + transaction type unless product explicitly allows parallel listing variants.
• Pricing version referenced by accepted application/offer/booking/agreement is immutable.

• Manager assignment intervals and permissions are property-scoped; assignment revocation does not delete historical
  actions.
• State transitions use compare-and-swap/version columns or row locks to prevent concurrent contradictory decisions.
• External callback/event IDs are unique where consumed; duplicate delivery must be harmless.
• Use partial indexes for open/active states and due workers; use GIN/JSONB only where schemaless attributes are genuinely
  needed.
• Do not store raw card data, full provider secrets, raw KYC documents or chat message content.


  7. Canonical domain state machines
  Account
     PENDING_VERIFICATION -> ACTIVE -> RESTRICTED | SUSPENDED | CLOSURE_PENDING -> CLOSED
     RESTRICTED/SUSPENDED -> ACTIVE only through authorized remediation/appeal.


  Ownership record
     DRAFT -> EVIDENCE_PENDING -> UNDER_VERIFICATION -> VERIFIED | REJECTED | CONFLICT
     VERIFIED -> REVERIFICATION_REQUIRED | TRANSFER_PENDING -> VERIFIED/TRANSFERRED.


  Property
     DRAFT -> ACTIVE -> RESTRICTED | TRANSFER_PENDING | ARCHIVED

  Listing
     DRAFT -> READY_FOR_REVIEW -> PUBLISHED -> PAUSED | WITHDRAWN | ARCHIVED
     PAUSED -> PUBLISHED after freshness/verification checks.
     Published listing may be system-paused for stale availability, moderation or authority expiry.


  Availability
     AVAILABLE | RESERVED | APPLICATION_UNDER_REVIEW | OFFER_ACCEPTED | OCCUPIED | TEMP_UNAVAILABLE | OFF_MARKET |
     SOLD | WITHDRAWN


  Inquiry/lead
     NEW -> ACKNOWLEDGED -> QUALIFIED -> VIEWING | APPLICATION | OFFER | BOOKING | CLOSED_WON | CLOSED_LOST


  Viewing
     REQUESTED -> CONFIRMED -> CHECKED_IN -> COMPLETED
     REQUESTED/CONFIRMED -> RESCHEDULED | CANCELLED | NO_SHOW


  Application
     DRAFT/RECEIVED -> SUBMITTED -> UNDER_REVIEW -> INFO_REQUESTED -> UNDER_REVIEW -> APPROVED | CONDITIONAL |

  8.1 API command rules
• All create/publish/approve/withdraw/decision/financial/external-side-effect commands use `Idempotency-Key` where
  duplicate execution could be harmful.
• PATCH requests use optimistic concurrency (`version` or `If-Match`) for business objects with concurrent
  owner/manager/admin modification risk.
• Sensitive actions require step-up authentication freshness; token age alone is not sufficient for payout/property-transfer
  actions.
• Pagination defaults to cursor-based for unbounded collections.
• Responses expose explicit DTOs; database rows and provider responses are never returned directly.

  14. Primary end-to-end journeys
  14.1 Onboard and verify a property
  1. Owner registers/authenticates in individual-owner-service.
  2. Owner completes account verification; service creates IDENTITY case in verification-service.
  3. Owner creates persistent property record and ownership claim.
  4. Owner uploads authority documents/media through media-document-service signed upload flow.
  5. Owner service creates PROPERTY_AUTHORITY verification case and attaches evidence refs.
  6. Verification result event/read-back updates verification link projection.
  7. When policy requirements pass, property becomes transaction-ready; this does not automatically publish a listing.
  8. Owner creates listing, pricing and availability, previews full customer cost and publishes.
  9. Publication transaction writes listing state + outbox event atomically; Marketplace consumes `listing.published.v1`.

                                                                   24
                                                                          COSMICFORGE REAL ESTATE | INDIVIDUAL OWNER BACKEND

14.2 Rent a property directly
1. Published listing is discovered through Marketplace projection.
2. Customer inquiry/viewing/application reaches owner domain with typed marketplace actor/customer references.
3. Owner communicates through CF Meet and system notifications are sent through Notification Service.
4. Owner reviews purpose-limited application evidence and records human screening decision.
5. Owner creates rental offer with immutable pricing snapshot.
6. Accepted offer creates agreement; signatures occur through e-sign adapter; artifacts stored via media service.
7. Rent/deposit obligations are created in owner domain and payment intents are executed by payment-service.
8. After required initial conditions are confirmed, tenancy enters PENDING_MOVE_IN then ACTIVE.
9. Move-in checklist, meters, keys/access and condition evidence are recorded.
10. During tenancy, payment-service events update obligations; owner can manage maintenance, notices and renewal.
11. Move-out/deposit settlement completes; property becomes available only after owner inspection/confirmation.

14.3 Sell or lease land / commercial property
1. Owner maintains verified parcel/commercial details and publishes correct transaction listing.
2. Buyer/business inquiry and offer are received; required verification/proof status is referenced, not copied unnecessarily.
3. Owner appoints professionals; data-room grants provide least-privilege document access.
4. Due-diligence findings and conditions are tracked against sale/lease transaction.
5. Payment milestones are requested through payment-service; unknown outcomes are reconciled.
6. Closing/possession/perfection checklist is completed with evidence; transaction completes only when configured
conditions pass.
7. Marketplace availability/listing projection is withdrawn/sold accordingly.

14.4 Operate a short-let
1. Owner configures calendar inventory, rates, stay rules, fees and cancellation terms.
2. Marketplace exposes date inventory projection.
3. Booking hold uses transaction/locking to prevent overbooking; confirmation requires required guest verification/payment
state.
4. CF Meet handles guest conversation; Notification Service handles system reminders.
5. Smart-access credential is issued for the stay period only.
6. Turnover job is scheduled around check-out/check-in.
7. Damage claim workflow may use deposit/payment-service and disputes without overwriting evidence.
8. Booking completes, access expires, reports update occupancy/revenue projections.

14.5 Appoint and revoke a property manager
1. Owner searches manager profiles from property-manager-service and reviews proposal.
2. Owner creates property-specific assignment with capabilities, spend limit, emergency rule, term and report schedule.
3. Owner service emits assignment-created event; manager service activates operational workspace.
4. Every manager action hitting owner service is authorized against active assignment and capability.
5. Permission changes are versioned and immediately propagated.
6. Revocation terminates capabilities and access grants immediately; property history remains intact.
7. Handover/report data is retained and ownership authority never changes.

15. Engineering additions required for completeness
Why this section exists
The V5 product document describes the desired product experience. The controls below are implementation necessities that
make those features safe and production-operable. They are additions to the backend specification, not changes to the
approved product vision.


Engineering addition                   Reason
Optimistic concurrency / fencing       Prevent two owner/manager/admin requests from making contradictory decisions on listing, pricing,
                                       application, assignment or transaction state.
Idempotency on commands                Required for publication, decisions, signature requests, external sync, payments, bookings, access
                                       grants and provider actions.
Transactional outbox                   Every cross-service event tied to a business state change is persisted atomically with that state.
Processed-event de-duplication         All consumed NATS events are at-least-once and must be harmless when duplicated.
Unknown outcome handling               External payment/e-sign/smart-access/calendar operations use read-back before repeating
                                       ambiguous side effects.
Capability-based service auth          Internal callers receive only the operations needed; valid service JWT does not equal unrestricted
                                       access.

                                       notice templates are configuration/versioned data, not constants.
Audit immutability                     Security, authority, consent, price, decision, payout, access, manager and dispute changes are
                                       append-only attributable audit events.
Retention/legal hold                   Deletion/anonymization jobs respect open dispute, transaction, financial and required record holds.
Privacy purpose binding                Document access is linked to active purpose, transaction and expiry, with revocation.
Rate limits / abuse controls           Gateway and service controls for auth, uploads, search-like actions, OTP/recovery and sensitive

Feature flags                          Provider/partner features such as WhatsApp, financing, insurance, external listing sync and smart

  18. Reliability, observability and recovery
• Expose `/health`, `/ready`, `/version` for API and worker processes.

Appendix D.1 Launch rule for unresolved gaps

falsely report success.
• The UI/Postman/OpenAPI must reflect actual supported behavior, not aspirational provider capability.

before production certification.
• No deferred provider is allowed to leak its vendor-specific types into core domain business logic.
